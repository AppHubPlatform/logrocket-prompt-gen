shoplc.com: performance with and without LogRocket

URL https://www.shoplc.com/ · Chrome (DevTools Protocol trace, V8 CPU sampler on) · Desktop 1350x940 · No CPU throttle (Lighthouse desktop preset, as GTmetrix uses), no network throttle · Cold isolated browser context per run · 3 runs with, 3 runs without, interleaved · Sept 24, 2026

LogRocket doesn't raise TBT and loads too late to affect LCP

Median TBT was 639ms with LogRocket and 750ms without (585ms to 682ms vs 701ms to 822ms). Every run with LogRocket had lower TBT than every run without it. Three runs per condition isn't enough to call that an improvement, but it does rule out a meaningful regression.

LogRocket's first network request started at 1.02s to 1.19s, after LCP in every run, so it can't affect LCP. Median LCP was 971ms with LogRocket and 1.06s without; that spread comes from server and network timing (TTFB ranged 32ms to 358ms).

Lighthouse-based tools (GTmetrix, PageSpeed) charge a whole long task to the first script that runs in it. On this page that is often LogRocket's exception-capture wrapper around other scripts' timers and animation-frame callbacks, so frames full of style recalc caused by the theme and third parties get billed to LogRocket.

How the misattribution happens

LogRocket's exception capture wraps setTimeout, setInterval, requestAnimationFrame and addEventListener, which lets it report errors thrown by any script. As a result, the function the browser calls to start many tasks is defined in LogRocket.min.js, even when the work inside belongs to Dynamic Yield, Shopify's web-pixels manager or the theme.

The worst case is a rendering frame. An animation-frame callback (a few ms, run through the wrapper) is followed by a full-page style recalc for DOM changes made by other scripts. Lighthouse bills the whole frame to LogRocket.

Why tools can show a regression anyway

Lighthouse measures TBT from FCP to Time to Interactive, the start of the first 5-second stretch with no long task. Here TTI landed between 5.22s and 6.23s in both conditions. A single long task near the end of that window pushes TTI out and adds whatever blocking happens in the extra time. Combined with billing wrapped callbacks to LogRocket, one unlucky single-run report can show a LogRocket "regression" that repeated runs don't reproduce.

What LogRocket does cost

LogRocket isn't free, and this report doesn't claim it is. LogRocket's own code accounted for 32ms to 140ms (median 134ms) of main-thread time inside long tasks. It runs in short, time-sliced chunks, so most of it never forms a long task of its own, and it doesn't show up as higher TBT.

The theme's loader starts LogRocket from requestIdleCallback(..., { timeout: 3000 }), which fired around 1.04s here, while the page was still loading. Waiting for the load event and then an idle callback would move LogRocket's startup out of the window lab tools score.

Methodology

  • Every run starts in a fresh isolated browser context, so the HTTP cache and storage are cold. The trace starts before navigation and stops about 10s after load.
  • Both conditions run the same init script, which patches Node.prototype.appendChild. In "without" runs it drops the cdn.logr-in.com script insert, so the LogRocket recorder never loads (verified on each run). LogRocket's Shopify app pixel (shopify-app-pixel.min.js) still loads in both conditions. It runs inside Shopify's web-pixel sandbox and records zero main-thread LogRocket time, so it doesn't affect the comparison.
  • No CPU or network throttling, matching Lighthouse's desktop preset. Runs alternate between conditions.
  • TBT = the sum of (duration minus 50ms) for main-thread tasks between FCP and TTI. TTI is the start of the first 5s window with no long task; this estimate ignores network quiet. "Fixed window" ends 20s after navigation start.
  • Ownership comes from V8 CPU profile samples on the page's main thread: each sample is charged to the script of the innermost JS frame. Samples with no JS on the stack count as browser work. "Lighthouse-style" charges the whole task to the URL of its first JS entry point.
  • LCP comes from Chrome DevTools' trace analysis.
  • Caveats: this is a lab test with three runs per condition, so small effects (under about 10%) are within noise. Tracing overhead (async stack capture, CPU sampling) applies to both conditions equally.
